# 백준 연동 구현 계획

상태: 계획 · 확인일: 2026-11-23 (KST) · 기준 브랜치: `master`

## 1. 범위와 근거

첫 버전은 스터디의 **문제 직접 추가**에서 백준 문제 링크나 번호를 받고, 사용자가 본인 풀이를 등록하면 상세 화면과 기간 집계에 반영한다. 확장 0.6.9에서는 팝업의 내 스터디에서 기존 웹 등록 폼으로 바로 이동할 수 있게 한다. 백준 계정 연결, 과거 풀이 자동 가져오기, 채점 결과와 코드 자동 수집은 공식 API 또는 운영사가 허용한 방식이 확인된 뒤 별도로 설계한다.

| 확인한 근거 | 이번 계획에 적용하는 사실 |
| --- | --- |
| [백준 재오픈 공지](https://acmicpc.net/board/view/166446) · [1000번 문제](https://acmicpc.net/problem/1000) | 서비스가 다시 운영 중이며 문제 링크는 `acmicpc.net/problem/{번호}` 형식으로 확인했다. |
| [백준 이용 규칙](https://help.acmicpc.net/rule) | 웹 스크래핑과 외부 도구의 자동 제출이 금지돼 있다. 자동 채점 확인이나 코드 수집에 사용할 수 있는 공식 연동 방식은 확인하지 못했다. |
| `src/app/api/groups/[id]/manual-solve/route.ts` · `src/lib/ledger.ts` | 기존 직접 추가는 로그인과 멤버십을 확인하고 `BOOK` 기록을 저장한다. 기존 풀이 원장과 코드 저장을 재사용할 수 있다. |
| `extension/popup-update.js` · [Chrome 업데이트 안내](https://developer.chrome.com/docs/extensions/develop/concepts/extensions-update-lifecycle) | 0.6.8에는 직접 업데이트 확인 버튼이 있다. 브라우저가 0.6.9를 다운로드할 수 있는 시점부터 버튼으로 받을 수 있다. GitHub 태그나 스토어 제출 성공은 공개 배포를 뜻하지 않는다. |

## 2. 구현할 흐름

1. 사용자가 백준에서 직접 제출하고 정답을 확인한다. 확장 팝업의 스터디 바로가기 또는 웹의 문제 직접 추가 화면을 연다.
2. 백준을 선택하고 `1000` 또는 `https://acmicpc.net/problem/1000`을 입력한다. 제목, 푼 날짜, 본인 코드와 언어를 입력한다. 제목을 비우면 «백준 1000번»으로 표시한다. 코드는 선택 입력으로 두고, 등록 후 같은 상세 화면에서 추가할 수 있게 한다.
3. 서버가 스터디 멤버십과 입력을 확인하고 `BOJ:1000`으로 본인 기록을 저장한다. URL을 받더라도 외부로 연결하지 않고 문제 번호만 추출한다. 동일 문제의 재전송은 최초 기록 날짜와 집계 건수를 유지한다.
4. 등록된 풀이 상세에서 원문 링크, 직접 등록 여부와 저장한 코드를 표시한다. 입력 또는 저장에 실패하면 폼에 이유를 표시하고 입력값을 유지한다.

## 3. 기존 코드와 변경 초안

| 위치 | 변경 제안 |
| --- | --- |
| `src/lib/platform.ts`, `src/lib/ingestValidation.ts` | `BOJ` 이름과 원문 링크를 추가하고 백준 문제 번호와 공식 호스트의 문제 URL을 정규화한다. 다른 주소나 잘못된 번호는 거절한다. 기존 책·기타 입력도 계속 받는다. |
| `ManualSolveForm.tsx`, 기존 `POST /api/groups/[id]/manual-solve` | 플랫폼 선택과 백준 번호 입력을 추가한다. 백준 분기에서 사용자 ID는 세션에서 얻고 기존 멤버십 검사와 원장 트랜잭션을 재사용한다. |
| `src/lib/ledger.ts`, 상세 및 프로필 표시 | 문제 번호를 풀이 식별자로 쓰고 직접 등록과 자동 검증을 구분한다. 상세·멤버 기록에 백준 라벨과 링크를 표시하고 내 프로필의 플랫폼별 표시를 확인한다. 기존 기간 집계와 같은 규칙을 적용한다. |
| `extension/popup.js` | 이미 조회되는 스터디별 `groupId`로 해당 스터디의 웹 등록 폼을 연다. 백준 사이트 접근 권한은 필요 없다. |

## 4. 저장 기반과 주의점

- PostgreSQL `platform` enum에 `BOJ`를 추가해야 한다. Drizzle 스키마와 저장소의 정본인 `scripts/migrate.mjs`를 함께 변경하고, 임시 DB에서 두 번 실행해 기존 기록과 재실행을 확인한다. 운영 DB 적용 여부는 아직 확인하지 않았다.
- 기존 `(userId, platform, problemSlug)` 고유 키가 플랫폼 간 번호 충돌을 막는다. 백준 수동 등록의 고정 이벤트 키를 쓰고, 같은 사용자가 같은 번호를 날짜를 바꿔 재등록해도 새 점수로 잡히지 않게 한다. 코드 변경은 기존 코드 저장 경로로 허용한다.
- 현재 장부는 `MANUAL_PENDING`도 집계한다. 백준도 이 규칙을 따르되, 직접 등록이라는 출처를 표시한다. 자동 확인된 기록으로 저장하지 않는다.

## 5. 구현과 검증 순서

1. URL·번호 검증 실패 사례를 먼저 만든 뒤 플랫폼 타입, DB 변경, 서버 입력 검증을 추가한다.
2. 비회원 등록 거절과 중복 기록 사례를 먼저 만든 뒤 기존 수동 등록 API를 확장한다. 정상 저장, 같은 번호 재등록, 코드 없는 등록 후 편집을 확인한다.
3. 정상 폼 이동과 기존 풀이 표시를 확인한 뒤 웹 폼, 백준 배지·링크, 확장 팝업 바로가기를 붙인다.

| 확인 위치 | 성공 및 실패 기준 |
| --- | --- |
| Vitest 입력·링크 테스트 | `1000`과 공식 문제 URL이 같은 번호가 되고, 외부 URL이나 잘못된 경로는 거절된다. |
| 임시 DB와 로그인 세션 | 멤버 한 사람이 한 문제를 여러 번 등록해도 한 건으로 집계되고, 다른 플랫폼은 영향을 받지 않는다. 비회원은 기록을 만들 수 없다. |
| 웹 및 확장 확인 | 팝업에서 해당 스터디 폼으로 이동한다. 저장한 코드와 원문 링크가 상세에 나타나고, 실패 시 폼 입력이 남는다. |
| 빌드 및 배포 | `npm test`, `npm run build`, `npm run ext:package`로 확인한다. 운영은 DB 마이그레이션 확인 → 웹 배포 → 확장 0.6.9 태그·스토어 제출 순서로 진행한다. |

## 6. 완료 기준

백준 한 문제를 본인이 등록하고 상세에서 코드를 다시 볼 수 있으며, 기간 집계에 한 건만 반영된다. 기존 플랫폼 등록도 계속 동작한다. 배포 후에는 Chrome 공식 업데이트 서버가 0.6.8에 0.6.9를 제공하는지 확인하고, 스토어 설치본에서 팝업 버튼을 눌러 버전이 바뀌는지 별도로 확인한다. 자동 감지는 공식 API 또는 운영사의 허용 범위 확인 후 다룬다.
